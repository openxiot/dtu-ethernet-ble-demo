0. 结论先行

第一次烧写（空片 / 新板）

烧什么：build/dtu-full.hex（Bootloader + App，不含 Meta），或只烧 bootloader.hex。

怎么烧：MRS GUI 推荐 / OpenOCD 命令行 / 只烧 Boot + 串口 IAP / WCH-LinkUtility。

关键：烧完 Meta 仍是 EMPTY，必须再用 .dtufw 走一次串口 IAP，设备才会进 App。

后续烧写（已有 Bootloader）

烧什么：只用 build/dtu-<ver>.dtufw，不再烧合并 hex。

怎么烧：网络 OTA 量产推荐 / 串口 IAP 现场推荐；SWD 只烧 App 仅供开发调试。

关键：整包由 Bootloader 搬运；SWD 直接烧 App 会绕过版本与签名校验。

场景烧什么方式
全新板 / 空片首次安装build/dtu-full.hex + 一次 .dtufwA MRS GUI（或 B OpenOCD）→ 串口 IAP
产线批量首次安装bootloader.hex + .dtufwC 只烧 Boot → 串口 IAP
现网设备升级.dtufw（服务器）A 网络 OTA
现场无网络 / 救砖.dtufwB 串口 IAP
开发调试改 Appobj/dtu-ethernet-ble-demo.hexC SWD 只烧 App（Erase All=false）
修复 / 升级 Bootloaderbootloader.hexD SWD 只烧 Boot（Erase All=false）
最容易踩的坑 MRS 默认 Erase All=true 会整片擦除。只烧 App hex 时它会连 Bootloader（0x0）和 Meta（0x28000）一起擦掉，设备无法启动。

1. 烧写对象：四个文件别搞混

文件内容用途
build/dtu-full.hexBootloader + App，不含 Meta初次烧写：SWD 一次写入
Bootloader/build/bootloader.hex仅 Bootloader（0x0–0x2FFF）只安装 / 修复 Bootloader
obj/dtu-ethernet-ble-demo.hex仅 App（0x3000 起）开发调试时 SWD 直接烧 App
build/dtu-<ver>.dtufw512 B 包头 + App 镜像 + RSA 签名串口 IAP / 网络 OTA 的唯一升级对象
hex 不是升级包，.dtufw 才是 hex 只用于 SWD 烧写；串口和网络升级都只认 .dtufw。合并 hex 不包含 Meta、Staging、Backup 区。

记住两条原则：

  • 初次烧写：先用 SWD 写入 dtu-full.hex（或只写 bootloader.hex），再用 .dtufw 走一次串口 IAP，写入 App 与 Meta。
  • 后续烧写：只用 .dtufw，优先网络 OTA，其次串口 IAP；不要再用 SWD 烧合并 hex，更不要整片擦除。

2. 初次烧写（空片 / 新板 / 整片重装）

目标：0x0 有 Bootloader、0x3000 有 App、0x28000 有 Meta 记录。共有四种方式：

方式烧写对象工具写 Meta适用场景
A. MRS GUIbuild/dtu-full.hexMRS 3 + WCH-Link否首次安装，推荐
B. OpenOCD 命令行build/dtu-full.hexMRS 自带 OpenOCD否无 GUI、脚本化 / 批量
C. 只烧 Boot + 串口 IAPbootloader.hex → .dtufwWCH-Link + USB-TTL是（IAP 写入）产线、手里没有 App hex
D. WCH-LinkUtilitybuild/dtu-full.hex需另装 WCH-LinkUtility否已装该工具时可选
先记住这个顺序 A / B / D 只写 Boot + App，Meta 仍是 EMPTY，烧完必须再走一次串口 IAP（方式 C 的第 4 步），否则 Bootloader 会无限等待、不会进 App。方式 C 本身就把 App 与 Meta 一起写入。

2.1 WCH-Link 接线

WCH-LINK板子
3V3VDD
GNDGND
SWDIOPA13
SWCLKPA14
RSTRST（建议接，下载器需要复位芯片）

串口升级另需 USB-TTL：TX→PA10、RX→PA9、GND→GND，115200 8N1。

2.2 方式 A：MRS GUI 烧合并 hex 推荐

  1. 生成合并 hex： 
    python3 tools/merge_hex.py Bootloader/build/bootloader.hex \
    obj/dtu-ethernet-ble-demo.hex -o build/dtu-full.hex
  2. 接好 WCH-Link，MRS 3 中右键工程 → Download Configuration：
    • Target Path = build/dtu-full.hex
    • Erase All = true（整片擦除，适合空片 / 重装）
    • Program / Verify / Reset = true
    这些设置保存在仓库根目录 .template（已被 git 跟踪）。
  3. 点击 Download 烧写。
  4. 复位后首次启动：Meta 仍是 EMPTY，Bootloader 无限等待串口升级。按方式 C 的第 4 步用 ota_uart.py 刷一次 .dtufw，写入 App 与 Meta。

2.3 方式 B：OpenOCD 命令行烧合并 hex

MRS 3 安装目录自带 OpenOCD（WCH wlinke 适配器），不打开 IDE 也能烧。macOS 路径：

OC="/Applications/MounRiver Studio 3.app/Contents/Resources/app/resources/darwin/components/WCH/OpenOCD/OpenOCD/bin"

Windows / Linux 对应 .../resources/app/resources/win32|linux/components/WCH/OpenOCD/OpenOCD/bin。先做只读连接检查：

"$OC/openocd" -f "$OC/wch-riscv.cfg" -c "init; halt; flash probe 0; exit"

正常应看到 Target successfully examined.、device id = 0x...、flash size = ...kbytes。然后烧写并复位：

"$OC/openocd" -f "$OC/wch-riscv.cfg" \
    -c "init; halt; program build/dtu-full.hex verify reset; exit"

等价于 MRS 里 Target Path=build/dtu-full.hex + Program/Verify/Reset，但 Meta 仍为 EMPTY，烧完同样要执行方式 C 的第 4 步。

OpenOCD 的边界
  • flash bank 只有前 160 KB（0x0–0x27FFF）；合并 hex 写到约 0x24xxx，在范围内；Meta / Staging 在 0x28000 之后，不能用 OpenOCD 写。
  • program 只擦除 hex 覆盖的扇区，不做 MRS 的 Erase All。
  • OpenOCD 不设置芯片 ROM/RAM 分配（128K+64K / 160K+32K 等）。新片或分配异常时，先在 MRS 里 Download 一次。
  • 某些 WCH-Link 固件会打印 The Chip type does not match，甚至报告 ROM 128 kbytes RAM 64 kbytes。若同时能 Target successfully examined 且 flash 大小正确，可继续；否则先用 MRS / WCH-LinkUtility 确认芯片配置、更新 WCH-Link 固件。

2.4 方式 C：只烧 Bootloader，再用串口 IAP 装 App 产线推荐

SWD 只写约 9 KB 的 Bootloader，App 与 Meta 都由串口 IAP 写入，适合产线批量。

  1. 构建 Bootloader，得到 Bootloader/build/bootloader.hex（见第 4 节）。
  2. MRS Download Configuration：
    • Target Path = Bootloader/build/bootloader.hex
    • 空片：Erase All = true；已有 App/Meta、只想修 Boot：Erase All = false
    • Program / Verify / Reset = true
  3. Download。复位后 Meta 为 EMPTY，Bootloader 停在串口等待升级。
  4. USB-TTL 接 PA9 / PA10 / GND，先运行工具，再复位设备： 
    python3 tools/ota_uart.py /dev/tty.usbserial-XXXX build/dtu-0.1.0.dtufw
  5. 工具握手后发送整包；Bootloader 校验 CRC32/SHA-256，写 Meta=STAGED，搬运到 App，再校验后跳转。至此 0x0、0x3000、0x28000 都有内容。

2.5 方式 D：WCH-LinkUtility 可选

如果机器上装了 WCH 官方的 WCH-LinkUtility（仓库不提供，需自行安装）：

  1. 连接 WCH-Link，选择芯片系列 CH32V208；
  2. 打开 build/dtu-full.hex；
  3. 勾选 Erase All（空片 / 重装）、Program、Verify、Reset；
  4. 点击 Program 下载。

同样只写 Boot + App，烧完 Meta 仍为 EMPTY，需要按方式 C 第 4 步走一次串口 IAP。不同版本工具界面可能略有差异，以实际界面为准。

2.6 为什么初次烧完还要串口 IAP

空片 │ SWD：dtu-full.hex（Boot + App） 或 SWD：bootloader.hex ▼ Meta = EMPTY → Bootloader 无限等待串口 │ USB-TTL：ota_uart.py build/dtu-x.y.z.dtufw ▼ 写 Meta = STAGED → 搬运 Staging → App → 校验 → Meta = APP_VALID → 跳转 App

合并 hex 不包含 Meta 区，也不包含 Staging / Backup。Bootloader 的判断完全依赖 Meta：EMPTY 时不会自行跳 App。串口 IAP 完成后写 STAGED，搬运成功再写 APP_VALID，设备才会正常启动。

如果产测工具能按 ota_meta_t 格式直接写入一条 APP_VALID 记录，也可以代替串口 IAP；否则串口 IAP 是最简单且能顺带验证升级链路的方式。

3. 后续烧写（已有 Bootloader 的板子）

原则：只升级 .dtufw 按现场条件选择网络 OTA 或串口 IAP。SWD 只用于开发调试或修复 Bootloader；不再整片烧合并 hex，也不要整片擦除。
方式烧写对象校验适用
A. 网络 OTA.dtufw（HTTPS 下载）CRC32 + SHA-256 + RSA-2048现网批量升级，推荐
B. 串口 IAP.dtufw（本地串口）CRC32 + SHA-256现场 / 产线 / 救砖，推荐
C. SWD 只烧 Appobj/dtu-ethernet-ble-demo.hex无（绕过升级校验）开发调试
D. SWD 更新 Bootloaderbootloader.hex无Boot 修复 / 升级，少见

3.1 方式 A：网络 OTA 量产推荐

  • 烧哪个：服务器上托管的 .dtufw。设备通过 HTTPS 下载到 Staging，再由 Bootloader 搬运到 App，不需要 SWD，也不需要人到现场。
  • 怎么触发：服务端在设备已连接的 WS 上发二进制 DTUO 通知（URL、大小、版本、CRC16）；设备回 ota=starting，断开 WS 后下载、验签、写 Meta、复位、搬运。
  • 结果：下次 WS 连接建立时设备上报 fw=x.y.z;hw=XXXXXXXX;ota=done，失败则 ota=failed;code=N。
  • 完整 TLV 格式与服务器要求见 第 7 节。

3.2 方式 B：串口 IAP 现场 / 产线推荐

  • 烧哪个：build/dtu-<ver>.dtufw（不是 hex）。
  • 怎么烧：USB-TTL 接 PA9 / PA10 / GND，先运行工具，再复位设备： 
    python3 tools/ota_uart.py /dev/tty.usbserial-XXXX build/dtu-0.2.0.dtufw
  • 进入条件：Meta 为 EMPTY / RECOVERY 时无限等待；BOOT_UART 等 30 s；APP_VALID 每次启动只留 500 ms 窗口，所以顺序必须是“先开工具，再复位”。
  • 默认拒绝降级；确需降级加 --allow-downgrade。协议和状态码见 第 6 节。

3.3 方式 C：SWD 只烧 App 仅开发调试

  1. MRS Download Configuration：
    • Target Path = obj/dtu-ethernet-ble-demo.hex
    • Erase All = false（否则 Bootloader 与 Meta 被擦除）
    • Program / Verify / Reset = true
  2. Download，复位。

这条路径绕过版本检查、包 CRC / SHA 与 RSA 验签，只适合开发调试。App 启动 30 s 后会把 Meta 的版本更新为实际运行版本；若新 App 起不来，累计 5 次后进入 RECOVERY。

3.4 方式 D：SWD 更新 Bootloader 少见

  • Target Path = Bootloader/build/bootloader.hex，Erase All = false，只擦写 0x0–0x2FFF，App 与 Meta 保持不变。
  • Bootloader 与 App 共用 User/ota_*.c 的 Meta / 包格式；升级 Boot 时保持两者兼容，改分区或 Meta 格式必须整片重装。
  • 更新后复位，Bootloader 按现有 Meta 继续启动 App。

4.2 编译 App

MRS 3 中 File → Open Folder… 打开仓库根目录（或命令面板执行 Open MRS Project），右键工程 → Build Project / ReBuild Project。产物：

obj/dtu-ethernet-ble-demo.hex    # 烧写 / 打包
obj/dtu-ethernet-ble-demo.elf    # 调试
obj/dtu-ethernet-ble-demo.map    # 体积分析

首次构建会生成 obj/makefile（含本机绝对路径，由 MRS 维护）。之后可用命令行增量构建：

make -C obj all
make -C obj clean

./build-app.sh       # 等价封装：自动定位工具链 + 校验 0x3000 起始 / 148 KB 上限

4.3 编译 Bootloader

make -C Bootloader          # 构建 + 自动检查 12 KB 上限
make -C Bootloader size     # 只打印体积并检查
make -C Bootloader clean

./build-bootloader.sh       # 等价封装：自动定位工具链 + 校验 0x0–0x2FFF

产物 Bootloader/build/bootloader.{hex,bin,elf,map}。Makefile 内置 size gate：text + data 超过 12288 字节直接失败（当前约 9060 字节）。

4.4 版本、hw_id、密钥

User/ota_config.h：

#define OTA_HW_ID      0x00000001u
#define OTA_FW_VERSION OTA_MAKE_VERSION(0, 1, 0)
#define OTA_BL_VERSION OTA_MAKE_VERSION(0, 1, 0)
  • 发布新版本：改 OTA_FW_VERSION → 重新编译 App → 打包时 --version 用同一个值；不一致时 mkfw.py 告警。
  • OTA_HW_ID 与打包 --hw-id 必须一致，否则设备拒绝（HW_MISMATCH=10）。
  • 仓库只带开发公钥。量产替换密钥：
openssl genrsa -out prod_private.pem 2048
openssl rsa -in prod_private.pem -pubout -outform DER -out prod_public.der
python3 tools/pubkey2h.py prod_public.der -o User/ota_pubkey.h

私钥不得入库；Bootloader 不做 RSA 验签，替换公钥后只需重新编译 App。

4.5 生成 .dtufw 固件包

./pack-firmware.sh                 # 版本取 OTA_FW_VERSION，默认 dev 私钥
./pack-firmware.sh --version 0.2.0 --key prod_private.pem

脚本会检查签名私钥与 User/ota_pubkey.h 内嵌公钥是否一致（网络 OTA 必须一致），并自动用同名 *_public.der 做打包后验签自检。等价命令：

python3 tools/mkfw.py --hex obj/dtu-ethernet-ble-demo.hex \
    --version 0.2.0 --hw-id 1 \
    --key tools/keys/dev_private.pem \
    --pub tools/keys/dev_public.der \
    -o build/dtu-0.2.0.dtufw

包结构：512 B 包头（DTUFW 魔数、文件 / 镜像大小、CRC32、版本、hw_id、SHA-256、RSA-2048 签名）+ 256 B 对齐镜像。签名对象为 SHA-256(header[0x000..0x040) || image)。镜像超过 148 KB 或 hex 不在 0x3000 区段时工具直接失败。

6. 串口升级细节（USART1）

6.1 如何进入升级状态

Meta 状态Bootloader 行为
EMPTY / RECOVERY无限等待串口升级
BOOT_UART等 HELLO 30 s，超时按 APP_VALID 处理
APP_VALID每次启动留 500 ms 窗口；收到 HELLO 就升级，否则 attempts+1 后跳 App
STAGED / COPYING先校验并搬运，不等待串口

标准操作：先运行 ota_uart.py（持续发 HELLO），再复位设备。500 ms 窗口较短，先启动工具、再按复位键即可稳定握手。

6.2 使用 ota_uart.py

python3 tools/ota_uart.py /dev/tty.usbserial-XXXX build/dtu-0.2.0.dtufw
参数默认说明
--baud115200必须与固件一致
--hello-timeout15 s等待 HELLO_ACK 的总时长（期间每 50 ms 发一次 HELLO）
--ack-timeout5 s单帧 ACK 超时
--allow-downgrade关BEGIN 时置降级标志

6.3 帧格式

A5 5A | ver(1)=01 | type(1) | flags/status(2 LE) | offset(4 LE) |
len(2 LE) | data(len ≤ 256) | CRC16(2 LE，覆盖 ver..data)
  • CRC16：CCITT-FALSE，初值 0xFFFF，多项式 0x1021。
  • 数据按 256 字节页发送，offset 必须等于已接收长度，每页一个 DATA_ACK。
type名称方向
0x01 / 0x81HELLO / HELLO_ACK主机 / Bootloader
0x02 / 0x82BEGIN / BEGIN_ACK主机 / Bootloader
0x03 / 0x83DATA / DATA_ACK主机 / Bootloader
0x04 / 0x84END / END_ACK主机 / Bootloader
0x05ABORT主机
0x06RESET主机

BEGIN 载荷 14 B：file_size u32 | file_crc32 u32 | version u32 | flags u16。END 后 Bootloader 校验整包 CRC32、镜像 CRC32、SHA-256 与包头；不符则回 END_ACK 状态码并结束会话；通过则写 Meta STAGED，搬运到 App 并再校验，成功后跳转，搬运 / 再校验失败进入 RECOVERY。

6.4 状态码

码名称常见原因
0OK
1BUSY设备忙 / 正在处理
2BAD_FRAMECRC16 错、帧长度错
3BAD_STATE未 BEGIN 就发 DATA / END
4NO_SPACE包内 image_size 超过 148 KB
5BAD_SIZE大小非 256 倍数、单页长度错、offset 跳变
6FLASH_ERRFlash 擦写失败
7CRC_MISMATCH整包 / 镜像 CRC 或 SHA-256 不符
8BAD_SIGNATURE仅网络 OTA（App 侧 RSA 验签失败）
9VERSION_REJECTED版本不高于当前，需 --allow-downgrade
10HW_MISMATCH包 hw_id 与设备不符
11BAD_PACKAGE包头字段非法
12BAD_MAGIC包头 magic 不是 DTUFW
安全边界 网络 OTA 在 App 侧验 RSA 签名；串口 IAP 只校验 CRC32 / SHA-256（Bootloader 不含 RSA），只保证完整性、不保证来源，依赖物理接触设备。

7. 网络 OTA 细节（HTTPS）

7.1 流程

  1. App 保持 wss 连接；服务端下发二进制通知（DTUO TLV）。
  2. App 校验通知，成功回文本 ota=starting，否则回 ota=failed;code=N。
  3. 回调返回后 App 关闭 WS/TLS，复用唯一的 TCP socket 连接固件服务器。
  4. HTTPS GET 下载整包到 Staging（0x2A000），要求 Content-Length 精确匹配。
  5. 校验包 CRC32、SHA-256、版本 / hw_id 与 RSA 签名，全部通过后写 Meta=STAGED 并复位。
  6. Bootloader 校验 Staging → 搬运到 App → 再校验 → 跳转。
  7. 下次 WS 连接建立时上报 fw=x.y.z;hw=XXXXXXXX;ota=done（失败则 ota=failed;code=N），随后清除待上报标志。

7.2 通知格式（WS binary，DTUO TLV）

偏移长度内容
04magic "DTUO"（44 54 55 4F）
41协议版本 = 1
51类型 = 0x10（OTA 通知）
62flags（bit0 = allow downgrade），LE
84file_size（.dtufw 总字节数），LE
124version（major<<16|minor<<8|patch），LE
162URL 长度 N（≤ 220），LE
18N固件 URL，必须 https://
18+N2CRC16/CCITT-FALSE，覆盖字节 [4, 18+N)，LE

总长度 20+N，限制在 20–240 字节。file_size 必须满足 512 + 256 ≤ file_size ≤ 512 + 148 KB，且 (file_size - 512) 是 256 的倍数。

7.3 通知帧生成示例

import struct

def crc16(data, crc=0xFFFF):
    for b in data:
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc

def ota_notify(url, file_size, version, flags=0):
    u = url.encode("ascii")
    assert u.startswith(b"https://") and len(u) <= 220
    body = b"DTUO" + bytes([1, 0x10]) + struct.pack("<HIIH", flags, file_size, version, len(u)) + u
    return body + struct.pack("<H", crc16(body[4:]))

# 版本 0.2.0 = 0x000200
frame = ota_notify("https://fw.example.com/dtu/dtu-0.2.0.dtufw", 152064, 0x000200)
# ws.send_binary(frame)

7.4 固件服务器要求

  • 只支持 HTTPS；TLS 1.2 套件 ECDHE-RSA-AES128-GCM-SHA256，服务器证书需 RSA-2048，证书链记录不超过 4096 字节。
  • 设备不校验服务器证书（MBEDTLS_SSL_VERIFY_NONE），完整性由包内 RSA 签名保证。
  • 必须返回精确的 Content-Length；不支持 chunked、Range、301/302 跳转。
  • URL 最长 220 字符，可带 query；支持域名（走 DNS）或 IPv4 字面量（直连，跳过 DNS）。
  • 下载期间设备只有一个 TCP socket，wss 会断开，升级完成后自动重连。
评审确认的安全约束 仅允许 https://；固件 URL 不做域名白名单；TLS 不校验证书；默认拒绝降级；Bootloader 未启用 WRP 写保护；私钥不入库。

8. 启动决策与恢复

Meta 状态行为
EMPTY无限等待串口 IAP
RECOVERY无限等待串口 IAP
STAGED / COPYING校验 Staging（Meta VERIFIED + 包头 SHA/CRC/尺寸/版本一致）→ 搬运到 App → 校验 → APP_VALID 并跳转；Staging 无效则改回 APP_VALID，搬运失败进入 RECOVERY
BOOT_UART等 HELLO 30 s：收到则升级，超时转 APP_VALID
APP_VALIDattempts ≥ 5 或 App 向量表非法 → RECOVERY；否则留 500 ms HELLO 窗口，尝试次数 +1，跳 App

App 启动 30 s 后调用 confirm_running()：写回 APP_VALID、attempts=0、版本以实际运行为准。累计 5 次上电都没撑过 30 s，下一次启动就进入 RECOVERY（防“新固件起不来”死循环）。

恢复步骤

  1. USB-TTL 接 PA9 / PA10 与 GND；
  2. 运行 python3 tools/ota_uart.py <port> <正常的 .dtufw>；
  3. 复位设备；工具握手后完成升级，Bootloader 搬运并跳转 App；
  4. 若仍失败，检查包版本 / hw_id / 签名以及串口接线。
