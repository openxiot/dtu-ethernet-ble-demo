1. 结论先行

建议采用 IAP，不采用 ISP。 串口升级和网络升级都由我们自己的 Bootloader + App 完成；芯片出厂的 ISP Bootloader 只保留为产线首烧与救砖手段。
问题结论
用 IAP 还是 ISP？IAP。ISP 需要 BOOT0 跳线、断电复位和 PC 端工具，出厂 Bootloader 不含以太网协议栈，无法做网络升级，也不适合现场设备。
「串口发送固件升级」是 ISP 吗？不是。串口升级是 IAP over UART：由我们的 Bootloader 接收镜像、写 Flash、校验、跳转。ISP 是芯片内部固化的下载模式。
网络升级怎么做？服务端在现有 WebSocket 上下发一条 OTA 通知（固件 HTTPS 地址、文件大小、版本号）；App 解析地址后关闭 WS，用同一个 TCP socket 建立 TLS 连接并发 HTTPS GET 下载 .dtufw 包，写入 Staging；校验签名后复位，由 Bootloader 搬运到 App 区。TLS 不做证书校验，只提供加密通道；固件真实性由包内 RSA 签名保证。
下载时 WS 还连着吗？不连。当前 WCHNET_NUM_TCP=1，WS 和 HTTPS 不能同时存在。App 先关闭 WS/TLS，再用同一个 socket 建立到固件服务器的 TLS 连接并下载；完成后复位，重启后重连并上报结果。不建议把 TCP 数提到 2（约多 2 KB RAM，会吃掉 TLS 余量）。
App 能不能自己覆盖自己？不能安全地做。运行中的 App 不能擦除自身代码区，因此必须有独立 Bootloader，并先把新镜像放到 Staging。
Flash 够不够？当前布局刚好占满 480 KB：App 144 KB、Staging 160 KB、Backup 152 KB。新增 HTTPS 客户端后 App 预计 135–140 KB，余量 4–9 KB，偏紧。真正的瓶颈是 160 KB 零等待区：App 槽 = 160 KB − Bootloader，三份镜像又把硬上限压到约 153 KB；详见 5.4 与决策 13。
升级失败会不会变砖？Bootloader 自身永不升级；只有 Staging 校验通过才会动 App 区；搬运中断可在下次启动重试；预留 Backup 区可扩展自动回滚。产线不开启 WRP，Bootloader 的保护依赖分区边界与代码约束。
要不要做 A/B 双分区？不推荐。A/B 只需两份镜像、回滚免费，但 CH32V208 只有 160 KB 零等待区，两个 144 KB 槽必有一个落在非零等待区，每隔一版运行变慢；还需两套链接地址、双构建和双包发布。方案与对比见 5.5，结论见决策 20。
需要改服务器吗？需要。服务端要能通过 HTTPS 托管 .dtufw 固件包（建议支持 Content-Length 与 Range），在 WS 上下发 OTA 通知，并处理设备重启后的版本/结果上报。
两条通道协议是否统一？统一在固件包上。串口按帧传输同一个 .dtufw 文件；网络用 HTTPS GET 下载同一个文件；设备端共用一套包头解析、CRC32/SHA-256/RSA 校验和 Staging 写入逻辑。

1.1 方案一句话

固定 Bootloader（0x0，16 KB）+ 固定 App（0x4000，144 KB）+ 双页元数据 + Staging / Backup（非零等待区）；App 负责通过 HTTPS 获取 .dtufw 包、校验并写入 Staging，Bootloader 负责启动决策、串口恢复和搬运；两条通道共用同一固件包格式与签名。串口升级只使用调试串口 USART1，不经过 RS-485 业务总线。

1.2 推荐落地顺序

  1. Phase 0：Flash 可行性验证（非零等待区擦写、0x08000000 别名、搬运跳转、耗时实测），以及单 socket 下的 HTTPS GET 验证（TLS 主机名参数化、VERIFY_NONE、握手 RAM/耗时）。
  2. Phase 1：Bootloader + 串口 IAP（仅 USART1）+ .dtufw 包 + 分区 / 链接脚本 / 合并烧录，先打通「不会变砖」的底线。
  3. Phase 2：网络 OTA（WS 通知 + HTTPS GET）+ 固件 HTTPS 托管 + 签名校验 + 结果上报。
  4. Phase 3：自动回滚、启动尝试计数、Range 续传、看门狗与产线流程。不再包含 RS-485 通道和 WRP。

说明：本文中的耗时为工程估算，带「需实测」标记的项必须在 Phase 0 用实板确认。

2.2 现有软件栈

  • 网络：WCHNET + DHCP/DNS + TCP + mbedTLS 1.2 + 自研 WebSocket 客户端，已稳定连上 ws.dtu.ap.openxiot.cn:443。
  • WS 缓冲：WS_FIFO_SIZE=512、payload[256]、WS_TX_SIZE=256。网络升级的 WS 通知只带 URL/大小/版本，控制在 240 B 以内，payload[256] 可保持不变；只有 URL 上限放宽到 220 B 以上时才需要扩到 320 B。
  • HTTPS 客户端：当前工程没有 HTTP/HTTPS 客户端。需要新增精简的 HTTPS GET 实现（URL 解析、TLS 建连、状态行、Content-Length、chunked、超时），复用 WCHNET socket、现有 DNS 服务器和 mbedTLS。
  • TLS：mbedTLS 目前只服务 WS，mbedtls_ssl_set_hostname(&ssl, DTU_HOST) 把主机名硬编码为 DTU_HOST；网络升级需要把 TLS 层抽成可复用的客户端，主机名参数化，供 WS 与 OTA 共用。OTA 连接保持 VERIFY_NONE，不做证书校验。
  • 调试串口：USART1，PA9(TX)，115200 8N1；当前 Debug/debug.c 只初始化了 TX，PA10(RX) 未配置。串口升级只在这个调试口上做，需要补 RX，并确认板子调试座引出 PA10。RS-485（USART2）不参与升级。
  • 服务端：DeviceYedS710YmProcessor 当前只处理心跳/csq/coordinates/查询帧，尚无 OTA 消息类型；固件需要放到支持 HTTPS 的静态服务器/对象存储。
  • 无 RTC / 无纽扣电池：TLS 证书有效期无法可靠校验，因此 OTA 的 TLS 连接采用 VERIFY_NONE；TLS 只保证传输加密，不承担固件真实性，完整性由包内 RSA 签名保证。
关键约束：执行位置 App 必须链接到 0x4000 并从零等待区执行；Staging / Backup 放在非零等待区，只读不执行。Bootloader 与 App 都不能在运行中擦除自己正在执行的页。

3. IAP 还是 ISP

3.1 两种方式对比

3.2 为什么网络升级只能是 IAP

ISP 的执行权在芯片内部固件，它只实现 USB/UART 下载协议，不跑 WCHNET、不跑 TLS，也没有我们的 WebSocket 会话。要让设备「联网自己升级」，必须由用户代码实现下载、校验、写 Flash 和重启切换——这就是 IAP。ISP 在这里只承担「设备彻底变砖后，用 WCH-Link 或 BOOT0+串口救回来」的角色。

3.3 串口升级也不是 ISP

「串口发送固件」有两种完全不同的做法：

  • ISP over UART：BOOT0 拉高、复位、WCHISPStudio 下载。需要现场有人操作跳线和 PC，不适合设备内部/远程触发。
  • IAP over UART：设备正常运行或停在 Bootloader，主机按自定义协议发送镜像；设备自己擦写、校验、重启。本文采用这一种。
选型结论 产品固件实现 IAP；产线保留 ISP 作为首烧与救砖；两者不冲突，但生产烧录必须使用「Bootloader + App」合并镜像，避免 ISP 只烧 App 导致 0x0 处没有 Bootloader。

4.2 为什么 Bootloader 不做网络下载

Bootloader 需要「小、稳、永不升级」。把 WCHNET + DHCP/DNS + TCP + mbedTLS 放进 Bootloader，Flash 至少增加 40–60 KB、RAM 增加 10 KB 以上，16 KB 的 Bootloader 区根本放不下，也会把最关键的恢复代码变得复杂。v1 的设计是：网络升级只在 App 正常运行时进行；App 损坏时靠串口恢复或 Backup 回滚。既然网络固件强制 HTTPS，Bootloader 做网络恢复还必须塞进 mbedTLS，更不现实。若产品要求「无人在现场且 App 已损坏也能联网恢复」，需要重新评估分区和 Bootloader 体积，而不是在本方案上打补丁。

4.3 单 socket 的取舍

WCHNET_NUM_TCP=1 是当前为省 RAM 做的配置。WS 和 HTTPS 都要 TCP，所以网络升级只能分时：先 WS 收通知，再关 WS，再建立到固件服务器的 TLS 连接并下载。代价是下载期间无法向服务端实时上报进度，结果要等设备重启重连后再报；收益是省下约 2 KB 静态 RAM，保住 TLS 握手余量。

如果产品明确要求“下载进度实时可见”，有三个选择：① 把 WCHNET_NUM_TCP 提到 2（约 +2 KB RAM，需重新实测 TLS）；② 下载期间用 UDP 发进度（新增服务端协议，不推荐）；③ 接受“开始/结束”两个状态，不做百分比。本文推荐 ③。

基线说明：上表是 v0.3 基线（Boot 16 KB / App 144 KB），也是当前代码可直接采用的布局。若按 5.4 的结论冻结 Boot 12 KB / App 148 KB @0x3000，只改 Boot 和 App 两行的边界：Boot 0x0000–0x2FFF（12 KB）、App 0x3000–0x27FFF（148 KB）；Meta/Staging/Backup 的地址与大小完全不变，其余约束继续适用。

0x08000000 别名 链接脚本用 0x00000000 段执行；但 FLASH_ROM_ERASE/WRITE、FLASH_ErasePage_Fast、FLASH_ProgramPage_Fast 的地址检查基于 FLASH_BASE=0x08000000。所有擦写/回读指针统一使用 0x08000000 + offset，不要传 0x0 基址，否则会被判为地址越界。

5.2 关键约束

  • 零等待边界：当前配置下 0x00028000 是零等待区终点。App 必须完整落在 0x4000–0x27FFF；Meta/Staging/Backup 不执行，放在边界之后。
  • App 链接地址：Ld/Link.ld 改为 ORIGIN = 0x00004000, LENGTH = 144K；Bootloader 使用单独的 Link_boot.ld（ORIGIN 0x0，LENGTH 16K）。
  • 链接地址固定：不做 A/B 双地址执行。所有镜像都按 0x4000 链接，Bootloader 只负责把候选镜像搬到固定 App 区，避免「同一份固件要按两个地址各编译一次」。
  • 对齐：镜像大小按 256 B 向上取整，尾部补 0xFF；CRC32/SHA-256 都按补 0xFF 后的完整镜像计算。
  • App 上限：144 KB；当前 128632 B，余量 18824 B。若后续功能增长超过余量，可把 Bootloader 缩到 12 KB（App 148 KB，Meta/Staging/Backup 地址不变）；容量账与增长路径见 5.4。
  • Meta/Staging 不参与执行：非零等待区读取会慢一些，但只用于搬运和校验，不影响业务实时性。

5.3 链接脚本示意

/* Ld/Link_boot.ld（Bootloader，16 KB 基线） */
MEMORY {
  FLASH (rx) : ORIGIN = 0x00000000, LENGTH = 16K
  RAM  (xrw): ORIGIN = 0x20000000, LENGTH = 32K
}

/* Ld/Link.ld（App，16 KB Boot 基线） */
MEMORY {
  FLASH (rx) : ORIGIN = 0x00004000, LENGTH = 144K
  RAM  (xrw): ORIGIN = 0x20000000, LENGTH = 32K
}

/* 若冻结 Boot 12 KB / App 148 KB（5.4 推荐），只改两处：
   Link_boot.ld : LENGTH = 12K
   Link.ld      : ORIGIN = 0x00003000, LENGTH = 148K
   Meta/Staging/Backup 地址不变。 */

RAM 仍为 32 KB；Bootloader 不需要 WCHNET/mbedTLS，但其静态缓冲和 2 KB 栈要从同一块 SRAM 里分配。Bootloader 运行结束后跳转 App，App 启动代码会重设 sp/gp/bss。

5.4.1 140 KB 时的实际占用

按 140 KB 镜像、各区域取最小尺寸（Staging 必须容纳 512 B 包头 + 镜像，向上取整到 4 KB）：

所以“140 KB 就把 480 KB 用完了”对当前表成立，但 32 KB 富余是分散在三个区里的，拼不起来给 App 用。App 槽想变大，只能缩 Bootloader。

5.4.2 三份镜像的硬上限

运行、下载、备份三份都要放时，设 App = A：

上限按 3A ≤ 480 − Boot − Meta − 0.5 估算，未计 4 KB 对齐；实际取整后通常少 1–4 KB。

超过“全速”上限后，App 会开始进入非零等待区；超过三份上限后，必须放弃 Backup、缩 Meta 或改用外部 Flash。结论是：三份镜像的硬上限约 153 KB；若要求全速运行，则为 144–152 KB（取决于 Bootloader 大小）。不是“再大一点就立刻崩”，但到点必须做取舍。

5.4.4 为什么必须在冻结前决定

  • v1 的 Bootloader 永不升级；Boot 大小、App 起点、Meta 地址都是 Bootloader 的编译期常量。
  • 出货后想把 App 槽从 144 KB 改成 148 KB，必须换 Bootloader；换 Bootloader 只能靠 SWD / ISP / 串口现场重烧，不能通过网络 OTA 下发。
  • 因此建议 Phase 0 通过后直接冻结 Boot 12 KB + App 148 KB @0x3000：Meta 仍在 0x28000，Staging / Backup 地址不变，Bootloader 只改“搬运目标地址 + 镜像长度”两个常量，App 只改 Link.ld 的 ORIGIN / LENGTH。
  • 如果 Phase 1 实测 Bootloader 能压到 8 KB（有 SHA-256 时不太现实），再考虑 0x2000 / 152 KB；不建议为 4 KB 把恢复代码压到 8 KB。
  • 构建加 size gate：App > 140 KB 警告，> 148 KB 直接编译失败（若冻结 148 KB），避免发版前才发现。
不要把 480 KB 当成可用 App 空间 可用 App = 160 KB − Bootloader；三份镜像又把它压到约 153 KB。Staging 和 Backup 的超配（160 / 152 KB）只是余量，不能给 App 槽用。若产品路线图明确 App 会超过 152 KB，现在就要评估外挂 SPI Flash 或放弃 Backup，不能等出货后再改分区。

5.5 备选方案：A/B 双分区（评估）

结论先说：当前项目不推荐 A/B A/B 的优点是两份镜像、切换不拷贝、回滚免费；但 CH32V208 只有 160 KB 零等待区，两个可执行槽必有一个落在非零等待区，每隔一版运行变慢。下面给出完整方案与量化对比，供评审；若 Phase 0 实测慢速槽可接受且发布管线能维护双构建，再重新评估。

A/B 双分区有两种常见形态：

  • A/B-1 执行切换型（真 A/B）：两个槽都可直接执行；Meta 记录活动槽；升级只写非活动槽，复位后直接跳到新槽；旧槽原样保留，回滚只需改 Meta。需要两个链接地址、两份镜像。
  • A/B-2 固定执行 + 交换型：两份镜像都链接到同一个 App 地址，非活动槽只作存储，Bootloader 启动时把候选镜像“换”到固定槽。要保留旧镜像供回滚，必须有第三块区域或 MCUboot 式的 scratch 交换算法；本质上又回到 5.1 的三区拷贝方案，或引入很高的复杂度。本节以 A/B-1 为主，A/B-2 的取舍见 5.5.11。

5.5.4 启动流程

Bootloader:
  meta = 读取双页中 seq 最大且 CRC 有效的记录
  if meta.pending_slot 有效且该槽镜像校验通过:
      meta.active_slot = meta.pending_slot; meta.pending_slot = 0xFF
  校验 active 槽（size + CRC32，可选 SHA-256）
  if 校验失败:
      若另一槽有效 → active = 另一槽（回滚）；否则 RECOVERY
  attempts++
  if attempts > 5:
      标记当前槽 BAD → 若另一槽有效则回滚；否则 RECOVERY
  跳转到 active 槽基址（0x4000 或 0x28000）

App（新版本）:
  正常运行 30 s → 写 Meta：confirmed=1, attempts=0
  上报 ota=done

切换不拷贝，只改 Meta 并跳转；启动校验约 0.1–0.3 s（CRC32；加 SHA-256 约 0.2–0.5 s，需实测）。Meta 每次写都走双页轮换，掉电不会同时丢两条记录。

5.5.5 网络升级流程

活动槽 A（0x4000）运行中:
  WS OTA 通知(url,size,ver) → 校验 → 回 ota=starting → 关闭 WS/TLS
  HTTPS GET → 读 512 B 包头 → 校验 target_slot=B、hw_id、版本
  镜像流式写入 Slot B（0x28000，跳过 512 B 包头），同时算 CRC32/SHA-256
  RSA 验签通过 → Meta：slotB=VERIFIED, pending=B → 复位

Bootloader:
  校验 Slot B → active=B → 跳 0x28000

新 App（B）:
  运行 30 s → Meta：slotB=CONFIRMED, attempts=0 → 上报 ota=done

下一轮:
  活动 B → 下载到 Slot A → 切回 A，如此交替
  • 下载期间活动槽 A 完全不被写，掉电/中断最多损坏非活动槽；旧版本始终可启动。
  • 升级包只含镜像（写槽时跳过 512 B 包头）；签名在下载阶段验证，Bootloader 启动时信任 Meta 的 verified 标志并做 CRC 复验，不在 Bootloader 里做 RSA（与 5.1 的网络路径一致）。
  • 串口升级同理：App 置 BOOT_UART + 目标槽后复位，Bootloader 用串口把镜像写入非活动槽并校验，再设为 pending。

5.5.7 性能影响（决定性因素）

  • Slot B 从 0x28000 开始，正好是零等待区之后的第一个地址；整个 Slot B 都在非零等待区，取指会插入等待周期。
  • A/B 交替升级意味着每隔一个版本就从慢速槽运行，不是“只有升级那一次慢”。这是 A/B-1 在本芯片上的根本代价。
  • 不能只把冷代码放慢速区：运行在 B 时整个 App 都在 B；除非把热点函数复制到 32 KB SRAM 执行，但这会吃掉 TLS/业务 RAM，且覆盖不全。
  • Phase 0 必须先测：把当前 App 链接到 0x28000，连续运行 30 min，测 TLS 握手耗时、WS 往返/心跳抖动、以太网丢包、RSA 验签耗时、主循环延迟。若下降超过 20–30% 或出现丢包，A/B-1 直接否决。

5.5.8 容量对比

  • A/B 只需两份镜像：Boot 16 + Slot A 144 + Slot B 144 + Meta 8 = 312 KB，剩余 168 KB，比 5.1 的三份镜像（480 KB 占满）更省 Flash。
  • App ≤ 144 KB 时两槽各 144 KB；Boot 缩到 12 KB 时两槽可各 148 KB（Slot A 0x3000、Slot B 0x28000，Meta 后移）。
  • 但 A/B 不解决零等待区限制：Slot A 可以全速，Slot B 永远在慢速区。它用“执行性能”换“回滚与容量”。

5.5.9 发布与服务端影响

  • 每个版本产出两份镜像、两个签名包（A 链接 / B 链接）；CI 必须同时构建、校验两份。
  • 服务端要记录每台设备的活动槽和版本，只下发“非活动槽”对应的包；包内 target_slot 不匹配则拒绝。
  • 回滚后设备上报旧版本，服务端要接受并拉黑失败版本；否则会立刻重推同一个坏版本。
  • 产线合并 hex 为 Boot + Slot A；Slot B 保持擦除，Meta 为 EMPTY；首次启动进入串口窗口或由产线写入 active=A。

5.5.11 结论

结论 A/B-1 架构干净、回滚免费、Flash 更省，但在 CH32V208 上被 160 KB 零等待区否决：两个可执行槽必有一个在慢速区，每隔一版运行变慢，且需要双构建/双包发布。A/B-2（固定执行 + 交换）要么退化成 5.1 的三区拷贝，要么需要 MCUboot 级 scratch 交换算法，没有收益。
建议：保留 5.1 的拷贝方案；按 5.4 冻结 Boot 12 KB / App 148 KB，Phase 3 用 Backup 实现回滚；若 App 超过 152 KB，优先评估外挂 SPI Flash，而不是改 A/B。若 Phase 0 实测慢速槽性能可接受且发布管线能维护双构建，再重新评估 A/B-1。

6.4 跳转到 App

typedef void (*app_entry_t)(void);

static void jump_to_app(void)
{
    app_entry_t entry = (app_entry_t)APP_BASE;   /* 0x4000 处是 _start 的 j handle_reset */

    __disable_irq();                              /* 关全局中断 */
    /* 停掉 Bootloader 的 UART/TIM；清 NVIC pending */
    for (int i = 0; i < 8; i++) NVIC->ICPR[i] = 0xFFFFFFFFu;

    entry();                                      /* App 的 handle_reset 会重设 sp/gp/mtvec/bss */
}

注意：不要读 *(uint32_t*)APP_BASE 当作函数指针——RISC-V 的镜像开头是一条指令（j handle_reset），不是地址表。直接跳到 APP_BASE 执行即可。

6.5 启动尝试计数与回滚

  • 计数：Bootloader 在跳 App 前 attempts++；App 连续正常运行 30 s 后写回 attempts=0。若达到 5 次仍未确认，进入 RECOVERY / 回滚。
  • 风险：用户快速反复断电 5 次（每次不足 30 s）会误触发 RECOVERY。可通过「确认时间缩短到 10 s」「次数提高到 8」或「默认关闭、仅产线开启」来权衡。
  • Flash 寿命：每次启动最多 2 次元数据写（attempts++ / 清零），两页轮换，约 5 万–10 万次启动后才接近 10 万次擦写规格；对 DTU 足够。
  • 回滚：若要求「新固件启动失败自动回旧版」，需启用 Backup 区：搬运前把当前 App 备份到 Backup；新 App 未确认时由 Bootloader 把 Backup 搬回 App。v1 可只预留空间，Phase 3 实现。

6.6 生产镜像

产线不能只烧 App：0x0 没有 Bootloader 时设备无法启动。构建输出一个合并 hex（Boot 0x0 + App 0x4000，中间 0xFF），用 WCHISPStudio 一次烧录；Meta 区保持擦除态（EMPTY），首次启动会进入串口升级等待或由产线工具写入 APP_VALID。产线不开启 WRP，后续返修仍可直接整片擦除重烧；Bootloader 的保护靠 App 只允许擦写 Staging/Meta、绝不触碰 0x0–0x3FFF。

7. 固件包与校验

7.1 打包流水线

串口和网络传的是同一个文件 升级包统一为 .dtufw：512 B 包头 + 补 0xFF 到 256 B 对齐的镜像。串口按帧传这个文件的字节流；网络用 HTTPS GET 下载这个文件。设备端只需要一套包头解析和校验逻辑。 
MounRiver 编译 App（链接 0x4000）
        │
        ├─ objcopy -O binary app.elf app.bin
        ├─ 按 256 B 补 0xFF → app_pad.bin
        ├─ 计算 image_crc32 / image_sha256 / file_size
        ├─ 填 512 B 包头（magic、版本、hw_id、尺寸、CRC、SHA-256）
        ├─ 对「包头前 0x40 B + 镜像」做 SHA-256，RSA-2048 私钥签名
        ├─ 签名写入包头 0x40..0x13F
        └─ 输出 app_x.y.z.dtufw（512 B 头 + 镜像）

发布：.dtufw 上传到 HTTPS 服务器 / 对象存储；PC 串口工具直接发送同一文件

7.2 包头格式（512 B）

0x0082header_size512

7.3 设备端校验顺序

网络路径由 App 做完整校验（CRC32 + SHA-256 + RSA）；串口路径由 Bootloader 做 CRC32 + SHA-256，v1 不做 RSA（物理接触视为授权，见 10.2）。两条路径共用包头解析与 CRC/SHA 代码。

  1. 早期预检：收到前 512 B 后检查 magic、header_size、file_size ≤ 512+144 KB、image_size 256 B 对齐、hw_id 匹配、版本策略。失败立即 NAK，不必传完。
  2. 流式校验：下载/接收过程中对 image 算 CRC32 和 SHA-256；对 header[0..0x40) 先算一次 SHA-256 初始块。
  3. 收尾：比对 image_size、image_crc32、image_sha256；用内嵌 RSA 公钥验证 signature。
  4. 落标志：全部通过后写 Meta STAGED + verified，source=network/serial。

7.4 为什么用 RSA-2048 而不是 ECDSA

  • 当前 mbedTLS 配置已启用 MBEDTLS_RSA_C、MBEDTLS_PKCS1_V15、MBEDTLS_SHA256_C、MBEDTLS_BIGNUM_C，握手本身就在用 RSA；验签不需要新增算法模块，只增加少量调用代码。
  • ECDSA 需要额外打开 MBEDTLS_ECDSA_C 等，Flash 和瞬时 RAM 都会增加；在本工程约 2.3 KB 的 heap 余量下不划算。
  • 签名 256 B 放在包头，不再单独占 WS/串口的一帧；网络路径中 Bootloader 不验签，只信任 App 写入的 verified 标志；串口路径由 Bootloader 自己校验 CRC/SHA 后写 STAGED，同样不涉及 RSA。

7.5 版本与降级

版本号同时出现在文本上报（fw=1.2.3;hw=yed-s710ym;ota=1）和包头中。默认拒绝低于当前版本的镜像；服务端如需回退，在 OTA 通知/串口 BEGIN 的 flags 中置「允许降级」，并记录审计日志。

7.6 构建工具

  • tools/mkfw.py：输入 elf/bin、版本、hw_id、私钥；输出 .dtufw 和元数据 JSON。
  • tools/ota_uart.py：通过调试串口 USART1 发送 .dtufw，支持断点测试。
  • tools/ota_https_server.py：本地静态 HTTPS 服务（自签证书即可，设备端 VERIFY_NONE），模拟固件托管与 Range。
  • tools/ota_ws.py：模拟服务端下发 OTA 通知。
  • tools/merge_hex.py：合并 Boot + App，供产线烧录。

8. 串口升级（IAP over USART1）

8.1 物理通道

通道引脚默认波特率备注
USART1（调试/日志口）PA9 TX / PA10 RX115200 8N1只使用这个调试串口。当前固件只配了 TX；升级需确认 PA10 已引出并接主机 TX。RS-485（USART2）不参与升级。

USART1 平时用于日志输出（只 TX）。补上 RX 后，App 可以把收到的 HELLO 当作升级请求：置 BOOT_UART 后复位。Bootloader 阶段独占 USART1，不打印日志，避免二进制协议帧与日志文本混在一起。

8.2 进入 Bootloader 的方式

  1. 上电握手窗口：每次复位后 Bootloader 先监听 500 ms，收到合法 HELLO 即停留并进入升级模式；否则跳 App。PC 工具以 50 ms 间隔持续发 HELLO 即可命中。
  2. App 请求：App 收到服务端/串口的升级命令后，置元数据 BOOT_UART，调用 NVIC_SystemReset()；Bootloader 看到该状态后等待 30 s。
  3. App 无效：直接进入串口升级，无限等待。
  4. 兜底：若 PA10 不可用或线路损坏，用 ISP（BOOT0 + WCHISPStudio）或 WCH-Link 恢复。

8.3 串口帧格式

┌────────┬──────┬──────┬──────────┬──────────┬───────┬──────────┬────────┐
│ A5 5A  │ ver  │ type │ status/  │ offset   │  len  │  data    │ crc16  │
│ 同步头 │ 1B   │ 1B   │ flags 2B │ 4B (LE)  │ 2B LE │  len B   │ 2B LE  │
└────────┴──────┴──────┴──────────┴──────────┴───────┴──────────┴────────┘
crc16 = CRC-16/CCITT-FALSE(poly 0x1021, init 0xFFFF)，覆盖 ver..data
数据最大 256 B；整帧最大 270 B

解析状态机：等待 A5 5A → 收 10 B 帧头 → 按 len 收 data+crc → 校验 CRC；失败则丢弃并重新找同步头。payload 内出现 A5 5A 不会误判，因为解析器在 data 状态按长度消费。

DATA 帧的 offset 是整个 .dtufw 文件的偏移，从 0 开始；前 512 B 就是包头。设备把所有文件字节按序写入 Staging（包头也写），校验时从 Staging 头部读包头，搬运时跳过 512 B。

9. 网络升级（WS 通知 + HTTPS GET）

控制面与数据面分离 WebSocket 只负责“通知”：服务端下发一条固定格式消息，包含固件包的 HTTPS 地址、文件大小、版本号。固件本体不经过 WS，设备收到通知后主动发 HTTPS GET 下载 .dtufw 包。传输层强制 TLS 1.2；设备不做证书校验（VERIFY_NONE），镜像真实性由 RSA 签名保证。

9.1 为什么这样分

  • 固件不挤占业务 WS：128 KB 固件若走 WS 分片，会长时间占用会话、ACK、心跳；HTTPS 下载是独立请求，服务端可用对象存储/CDN 承载。
  • 服务端简单：固件作为 HTTPS 静态文件托管，支持 Content-Length 和 Range 即可；WS 只需要下发 URL 和接收结果。
  • 可复用 HTTPS 生态：断点续传（Range）、缓存、CDN、访问控制、下载统计都可直接用。
  • 设备端可控：下载是设备主动发起的 GET；本版不做域名白名单，但镜像必须通过 RSA 验签。
单 socket 约束：下载前必须关闭 WS 当前 WCHNET_NUM_TCP=1，WS 和 HTTPS 不能同时存在。流程是：收到通知 → 解析 URL → 回复“开始升级” → 关闭 WS → 用同一个 TCP socket 连接固件服务器（DNS → TCP → TLS）→ HTTPS GET → 写 Staging → 校验 → 复位。关闭 WS 会释放 WS 的 TLS 上下文，随后为 OTA 重新初始化 TLS；两次握手不重叠，RAM 峰值不叠加。下载期间没有 WS，进度无法实时上报；结果在设备重启重连后上报。若必须实时进度，需要把 WCHNET_NUM_TCP 提到 2，静态 RAM 约增加 2 KB，会吃掉 TLS 握手余量，不推荐。

9.2 WS OTA 通知格式

建议用紧凑二进制 TLV，不用 JSON：设备端无需引入 JSON 解析器，字段固定、长度可控。整条消息控制在 240 B 以内，正好落在现有 payload[256] 内。

┌──────────────┬──────┬──────┬──────────┬──────────┬──────────┬─────────┬───────┬───────┐
│ 44 54 55 4F  │ ver  │ type │ flags    │ file_size│ version  │ url_len │  url  │ crc16 │
│ "DTUO" 4B    │ 1B   │ 1B   │ 2B (LE)  │ 4B (LE)  │ 4B (LE)  │ 2B (LE) │ N B   │ 2B LE │
└──────────────┴──────┴──────┴──────────┴──────────┴──────────┴─────────┴───────┴───────┘
type = 0x10 (OTA_NOTIFY)
flags: bit0=允许降级, bit1=强制升级, bit2=保留
file_size = 整个 .dtufw 文件大小（512 B 包头 + 补 0xFF 的镜像）
url = "https://host[:port]/path/file.dtufw"（UTF-8，不含空格/控制字符）
crc16 = CRC-16/CCITT-FALSE，覆盖 ver..url
整条消息 = 20 + N 字节；N ≤ 220 时 ≤ 240 B，现有 payload[256] 足够

可选增强：在 version 后增加 file_crc32（4 B），设备下载完先比对整个文件 CRC；不增加也不影响正确性，因为包头里有更细的校验。若服务端坚持 JSON，可改成一条文本消息，但设备端需要额外的字符串解析和边界检查，建议只在联调阶段使用。

9.3 URL 校验

检查项规则失败处理
长度≤ 220 B（与 payload 匹配）丢弃通知，上报 BAD_URL
scheme只接受 https://；http://、其他 scheme 一律拒绝回 NAK，不发起下载
authority必须有 host；禁止 userinfo（user:pass@）；端口可省略（默认 443）或显式给出 1–65535拒绝
host不校验域名，不维护白名单（评审决定）；只要求是合法的 DNS 名或 IPv4 字面量解析失败则在 DNS 阶段中止

不做域名白名单意味着：WS 被劫持或服务端失陷时，设备可能被指向任意 HTTPS 主机。但攻击者没有签名私钥，无法让设备接受恶意镜像；实际风险是带宽消耗、下载失败和隐私泄露，而不是固件被替换。若后续需要收敛，可把白名单做成可选配置，不影响包格式。TLS 也不校验证书，因此它只提供加密，不提供对端身份认证——真实性完全由 RSA 签名承担。

9.4 HTTPS 客户端要求

  • URL 解析：拆出 scheme/host/port/path；host 同时用于 DNS、TLS SNI 和 Host 头。
  • TLS：TLS 1.2，VERIFY_NONE，不校验证书链、有效期和主机名；host 为域名时 SNI 设置为该域名，以兼容多域名/虚拟主机；host 为 IPv4 字面量时跳过 SNI。
  • 请求：GET /path HTTP/1.1、Host:、Connection: close、User-Agent: DTU/1.0；续传时加 Range: bytes=N-。
  • 响应：接受 200 OK（完整）和 206 Partial Content（续传）；必须校验 Content-Length（或 Content-Range）与通知里的 file_size 一致。
  • 分块：支持 Transfer-Encoding: chunked（对象存储常见）；也支持直接按 Content-Length 读。两者取其一，不能同时出现。
  • 重定向：v1 不跟随 3xx（包括跳到另一个 HTTPS 地址）；服务端应直接给最终 URL。
  • 超时：DNS 5 s、TCP 连接 5 s、TLS 握手 10 s、响应头 10 s、body 空闲 10 s、总时长 5 min；任一步超时即中止，保留旧 App。
  • 错误：TLS 握手失败、4xx/5xx、Content-Length 不符、body 提前断开 → 记状态、关闭 socket、重连 WS 上报失败；v1 不自动重试，等服务端重新通知。

9.6 下载失败/中断

  • 通知阶段失败：URL/版本/大小不合法，WS 还开着，直接回 NAK，不需要关连接。
  • TLS 失败：DNS、TCP 或 TLS 握手失败 → 关闭 socket，重连 WS，上报 ota=failed;code=...；旧 App 继续运行。
  • 下载中断：App 保留 Staging 但 Meta 仍为 APP_VALID；关闭 socket，重新连接 WS，上报 ota=failed;code=...；服务端可重新下发通知（v1 从 0 重传）。
  • 校验失败：清除 Staging 有效标记（或直接忽略），上报 BAD_SIGNATURE/CRC_MISMATCH；旧 App 继续运行。
  • 复位前掉电：Meta 未写 STAGED，旧 App 正常启动；Staging 残留不影响。
  • 结果上报：Bootloader 搬运成功时置 Meta flags.bit2（升级完成待上报）。新 App 首次连上 WS 读到该位，发一次 fw=1.2.3;hw=...;ota=done，然后清 bit2；失败路径由旧 App 发 ota=failed;code=...。这样重启后不会每次连接都重复上报 done。

9.7 断点续传（可选）

v1 从 0 重传。若现场网络差，可每 4 KB 把“已收长度 + 文件 CRC 中间值”写入 Meta 的 STAGED 记录；重新下载时先发 Range: bytes=N-，服务端返回 206 后从 N 继续。设备必须回读 Staging 已写部分重算 CRC32/SHA-256（不保存哈希中间态），并确认 Content-Range 匹配。要求固件服务器支持 Range；对象存储一般默认支持。

9.8 服务端职责

  1. HTTPS 托管：把 .dtufw 作为静态文件提供，返回准确的 Content-Length；证书可以是公网 CA 或自签（设备不校验），但建议用有效证书，避免中间设备/合规问题。建议支持 Range，不要用 chunked（设备端两种都支持，但定长更简单）。
  2. 下发通知：在设备 WS 会话上发 OTA_NOTIFY；URL 可使用带过期时间的签名 URL（设备不校验域名，只校验 URL 语法和镜像签名）。
  3. 版本策略：按 model/IMEI/版本/白名单灰度；记录谁被通知、谁成功。
  4. 结果收集：设备重连后上报 ota=done/failed，服务端更新升级状态；失败可按策略再次通知。
  5. 并发控制：同一 IMEI 同时只允许一个 OTA 会话；沿用现有 close_dup 退避。

10. 安全设计

10.1 威胁模型

  • 中间人：HTTPS 使用 VERIFY_NONE，链路是加密的但不认证对端；攻击者可以冒充固件服务器返回任意文件。包内 RSA 签名是唯一能阻止恶意镜像的机制。
  • 服务端被攻破/误操作：攻击者拿到 OTA 通道和通知能力，可以指向任意 HTTPS 地址；没有私钥仍无法构造可接受的镜像。
  • 无域名白名单：WS 被劫持或服务端失陷时，设备可能被引到任意主机，造成带宽消耗、下载失败或地址泄露；这是已接受的可用性/隐私风险，不是固件替换风险。
  • 物理串口访问：攻击者接触调试串口，通过 USART1 刷入任意镜像；物理接触按授权处理，串口路径只做 CRC32/SHA-256。
  • 降级攻击：回滚到有漏洞的旧版本。

10.2 分层防护

层措施优先级说明
镜像真实性RSA-2048 签名（PKCS#1 v1.5 + SHA-256），公钥内嵌 App，私钥离线必须无论 TLS 是否被攻破，设备只接受签名有效的镜像；复用现有 mbedTLS RSA 模块。
传输机密性控制面继续使用 wss + TLS 1.2；固件下载强制 HTTPS（TLS 1.2）必须评审决定：网络固件只能通过 HTTPS 下载，不接受明文 HTTP。
下载地址只接受 https://；校验长度、authority、path、file_size；不校验域名，不跟随重定向已确认评审决定不做 host 白名单。签名仍是最终防线；风险是可用性/隐私而非固件替换。
服务端身份不校验证书（VERIFY_NONE）；TLS 仅提供加密已确认无 RTC，证书有效期无法可靠校验；接受中间人可返回任意包的风险，由 RSA 签名兜底。
防降级版本单调递增；低于当前版本默认拒绝，force 需签名/授权建议服务端记录审计；串口 force 仅产线使用。
物理串口校验 CRC32 + SHA-256，不验签按需物理接触视为授权；若要求与网络一致，则在 Bootloader 内集成 RSA 验签（预计 +6–8 KB，需评估 16 KB 预算）。
Bootloader 保护产线不开启 WRP；App 侧 Flash 写入范围硬限制在 Staging/Meta，运行时不擦 0x0–0x3FFF已确认评审决定不开写保护；返修可直接整片擦除重烧，保护靠代码约束而非硬件。
调试口量产可关闭调试/限制 SWD按需与产线返修流程权衡。

10.3 验签流程

  1. 网络下载时，App 对包头前 0x40 B 和整个镜像增量计算 SHA-256，同时计算 image CRC32；串口接收时由 Bootloader 做 CRC32/SHA-256（不验签）。
  2. 收完后从包头读出 256 B RSA 签名；使用内嵌公钥做 mbedtls_rsa_pkcs1_verify(MBEDTLS_RSA_PUBLIC, MBEDTLS_MD_SHA256, hash, sig)。
  3. 只有包头字段、CRC32、SHA-256、RSA 全部通过，才写 Meta STAGED + verified。
  4. 网络路径：Bootloader 信任 App 写入的 verified 标志，只做 CRC 回读校验；串口路径：Bootloader 自己完成 CRC32/SHA-256 后写 STAGED。两条路径都不需要 Bootloader 集成 mbedTLS。

10.4 密钥管理

  • 私钥只存在于构建机/签名服务，离线或 HSM 保管；不进入仓库、不进入设备。
  • 公钥（DER SPKI 或 modulus/exponent）内嵌 App；包头 reserved 可预留 key_id，便于未来轮换。
  • 轮换：新公钥随新 App 一起发布；Bootloader 不验签，因此无需更新 Bootloader。
  • 泄露应急：发布带新公钥的 App（旧版本仍可能被旧 key 签名，需服务端/设备版本策略配合）。

11.2 异常处理原则

  • 先验后写：Staging 的 CRC32/SHA-256/签名全部通过后才写 STAGED；STAGED 后才允许动 App 区。
  • 可重入：搬运是幂等的（擦一页、写一页、校验），重复执行不会更坏。
  • 不信任声明长度：OTA 通知/BEGIN 的 file_size、包头里的 file_size/image_size、HTTP Content-Length 必须三者一致，且 ≤ 512+144 KB、256 B 对齐；否则拒绝，避免越界擦写。
  • HTTPS 异常：DNS/TCP/TLS 握手失败、404/500、body 提前断开、Content-Length 不符、chunked 解析错、超时 → 中止下载，关闭 socket，重连 WS 上报失败；Staging 残留不影响旧 App。
  • 读回校验：每页写完可选读回比较；搬运完成后对整个 App 区做 CRC32。
  • Flash 错误：FLASH_ROM_ERASE/WRITE 后回读失败 → 重试 1 次 → 仍失败则 NAK/ABORT，保持 App 可用。
  • 看门狗：App 建议启用 IWDG（2 s），主循环喂狗；单页擦写毫秒级，不会误触发。Bootloader 搬运循环喂狗或暂不启用。
  • Meta 写坏：两页都无效 → 进入 RECOVERY，等待串口；这是最后的兜底。

11.3 Backup / 自动回滚（Phase 3）

若产品要求「新固件启动失败自动回旧版」：搬运前先把当前 App 复制到 Backup 并校验；新 App 连续 N 次未确认启动则把 Backup 搬回 App。代价是每次升级多 1–2 s 搬运、Meta 多一个状态、Bootloader 代码略增。分区已预留 152 KB，可随时启用。

11.4 变砖边界

  • Bootloader 本身：不参与升级；产线不开启 WRP，正常升级路径不会写 0x0–0x3FFF，但 App 若越界写仍可能破坏它，因此 Flash 写入范围检查是必须的。彻底损坏时用 ISP 整片擦除或 SWD 重烧。
  • App + Staging + Meta 全坏：设备停在 RECOVERY，等待串口；远程无法恢复。若不可接受，必须启用 Backup 或网络恢复 Bootloader。
  • 恢复手段：WCH-Link SWD（无需 BOOT0）；或 BOOT0=高 + WCHISPStudio 串口/USB。

16. 决策记录（已确认）

以下为评审确认结果；未特别说明的按推荐值执行。包头字段、WS 通知格式和 Flash 分区建议在 Phase 0 通过后冻结。

#问题结论影响
1串口升级走哪个口？只走调试串口 USART1 PA9/PA10；RS-485（USART2）不参与升级。需确认 PA10 已引出
2网络升级是否采用「WS 通知 + HTTPS GET」？是。WS 只传 URL/大小/版本；固件走 HTTPS，不挤占业务 WS。服务端要 HTTPS 托管固件、下发通知
3串口与网络是否共用同一固件包？是。.dtufw = 512 B 包头 + 镜像；两条通道传同一文件。打包工具/校验逻辑统一
4网络镜像是否强制 RSA 签名？强制；复用现有 mbedTLS RSA/SHA-256。私钥离线。App +2–4 KB，验签 +1–2 KB RAM
5固件下载用 HTTP 还是 HTTPS？只允许 HTTPS（TLS 1.2），放在 Phase 2 实现；http:// 一律拒绝。每次 OTA 增加 TLS 握手 2–5 s
6是否做固件 URL 的 host 白名单？不做域名校验；只校验 scheme=https、长度、authority、path 和尺寸。接受被指向任意 HTTPS 主机的可用性/隐私风险，由 RSA 签名兜底。实现简化；无 host 收敛
7WS 通知用二进制还是 JSON？二进制 TLV（≤240 B，复用 payload[256]）；JSON 只用于联调。设备端免 JSON 解析
8下载期间是否关闭 WS？关闭。WCHNET_NUM_TCP=1；接受“开始/结束”两个状态，不做百分比。无法实时进度；省 2 KB RAM
9是否要求自动回滚？v1 不启用；先预留 152 KB Backup，Phase 3 视现场要求开启。回滚增加搬运时间与 Meta 状态
10是否启用启动尝试计数？启用（5 次 / 30 s 确认）；Phase 3 落地。每次启动写 Meta
11Bootloader 要不要网络恢复？v1 不做；App 损坏靠调试串口/Backup。强制 HTTPS 后 Bootloader 还需 mbedTLS，更不可行。Bootloader 体积/复杂度
12500 ms 启动串口窗口是否可接受？可接受；可缩短到 200–300 ms，代价是 PC 工具更难命中。正常启动延迟
13App 144 KB 是否够？当前 128.6 KB + OTA/HTTPS 预计 135–140 KB，余量 4–9 KB，偏紧。本版结论：Phase 0 通过后冻结 Boot 12 KB + App 148 KB @0x3000，Meta/Staging/Backup 地址不变；构建加 size gate（>140 KB 警告，>148 KB 失败）。详见 5.4。Bootloader 不能 OTA，边界必须一次定对
14HTTPS 断点续传是否 v1 就做？Phase 3；v1 失败从 0 重传。要求服务器支持 Range。增加 Range/checkpoint 逻辑
15TLS 是否开启证书校验/公钥固定？不校验（VERIFY_NONE）；TLS 只提供加密，镜像真实性由 RSA 签名保证。无证书链 RAM/Flash 开销
16产线是否开启 WRP 保护 Bootloader？不开启；保护依赖分区边界与 App 写入范围检查，返修可直接整片擦除。无写保护/恢复流程
17OTA 触发策略？服务端按版本/白名单灰度；设备不主动轮询。服务端策略
18升级期间业务策略？暂停业务上报与串口/485 转发；结束后恢复。服务端标记设备“维护中”。业务可用性
19串口升级是否要求 RSA 验签？v1 只校验 CRC32/SHA-256，物理接触视为授权；若要求与网络一致，Bootloader 集成 RSA（预计 +6–8 KB）。Bootloader 体积
20是否采用 A/B 双分区？不采用，保留拷贝方案。A/B 的执行槽必有一个在非零等待区，性能按版本交替下降；且需双链接地址、双构建、服务端双包。详见 5.5；若 Phase 0 实测慢速槽可接受且发布管线支持，再重新评估。性能与发布流程
本版（v0.4）新增 5.4 容量规划与增长路径，建议冻结 Boot 12 KB + App 148 KB @0x3000；5.5 A/B 双分区备选方案及量化对比，结论为不采用；决策表新增第 20 条。v0.3 已确认的串口仅 USART1、网络强制 HTTPS、无 host 白名单、TLS VERIFY_NONE、产线不开启 WRP 均不变。
